- `API_BASE_URL=https://recallstack-git-93054085833.asia-south2.run.app/api/v1`
- `WEB_BASE_URL=https://www.reasonai.tech`
- `SUPABASE_URL=https://jlqawpdsyptfxspyqnsu.supabase.co`
- `SUPABASE_ANON_KEY`: public publishable/anon key, never a service role or secret key.
- `BUILD_SHA`: actual Git source commit, generated by the build helper.
- `HACKATHON_JUDGE_MODE=false`.

`tool/prepare_build.dart` validates and writes ignored `build/verified-defines.json`. The four `MOBILE_*` repository variables support CI. Do not copy server environment files into mobile assets. `.env`, keystores and signing properties remain ignored. Production validates HTTPS/public key/source SHA and rejects judge mode. Android main/release disables cleartext traffic and backups; the debug manifest alone permits local development HTTP. Only INTERNET is requested by the main application. OAuth callback is `com.recallstack.app://login-callback` on both platforms; it must remain allowlisted in Supabase. Auth errors do not log session payloads.

## Reproducible verification and packaging

Use Flutter **3.32.5 / Dart 3.8.1**. Android SDK 36, AGP 8.9.1, Gradle 8.12, NDK 27.0.12077973, minimum Android API 24. Kotlin incremental compilation is disabled because Windows pub cache and workspace may live on different drives.

```powershell
cd mobile
flutter pub get
dart run build_runner build --delete-conflicting-outputs
dart format .
flutter analyze
flutter test
dart run tool/prepare_build.dart build/production-defines.json
flutter test integration_test/mobile_workflow_test.dart -d <device> --dart-define-from-file=build/verified-defines.json
flutter build apk --debug --target-platform android-arm,android-arm64,android-x64 --dart-define-from-file=build/verified-defines.json
flutter build apk --release --dart-define-from-file=build/verified-defines.json
flutter build appbundle --release --dart-define-from-file=build/verified-defines.json
```

The device integration test mocks **all authentication and network services**. It exercises device UI, SQLite drafts and navigation, without contacting production, consuming AI/sandbox budget, or proving real OAuth/judging. The normal debug APK uses the public production configuration and includes no test entry point. Do not distribute an integration-test APK as the app.

Android device testing requires ARM, ARM64 or x86_64. The current SQLite native dependency does not ship 32-bit x86; an old x86-only emulator cannot validate persistence. Delivery/debug CI explicitly target the three supported ABIs. Production release uses Flutter's supported release ABIs.

Install a verified APK with `adb install -r <apk>` or copy it to Android, allow installation from the chosen file app, and open it. If an older installation is signed with a different certificate, use a separate test device/profile or back up drafts before choosing to uninstall; never silently delete app data.

## Release gates and remaining external dependencies

1. **Android release signing:** completed locally with owner approval for candidate 5. APK and AAB signatures match the tracked public certificate; release is non-debuggable and cannot fall back to the debug key. The private PKCS12 keystore is outside Git, and `android/key.properties` remains ignored. The owner still needs an encrypted off-device backup; CI signing credentials and Play Console enrollment have not been configured. See [signing instructions](android-release-signing.md).
2. **Live authentication and backend smoke test:** Real Google OAuth callback, authenticated Run/Submit, server-persisted history/report, account switch and logout must be exercised with an authorized learner on the signed candidate. Mocked tests cannot satisfy this gate. No certification batch or 375-fixture revalidation is required.
3. **iOS:** Windows has no Xcode. Mobile CI includes a macOS unsigned release compilation with public production configuration. Even a passing unsigned build does not prove Apple provisioning, signing, archive/export or physical-device OAuth. Apple team/certificates/profiles and device testing remain separate gates.
4. **Saved-story discovery:** Mobile reconciles saved state for encountered stories and labels its saved list as device-local. The repository now includes `GET /knowledge/saved-stories` for the web feature, but production deployment and mobile adoption have not been verified in this refinement. Historical saved stories from another device are not claimed to be discoverable in the current mobile cache.
